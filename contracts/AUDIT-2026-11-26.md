# self-audit / every contract that holds money, 2026-11-26

READ THIS FIRST: this is a self-audit. It was done by the same AI tooling that wrote the contracts, so it
shares their blind spots. It is not an independent audit and must not be presented as one ("audited by")
anywhere public. Say "internally reviewed, not independently audited".

## method

1. line-by-line read of each contract, every external call and every place value moves.
2. per contract: who can call what, what the worst caller can do, what a hostile token / recipient /
   pool state can do, reentrancy, rounding, overflow casts, return-data handling.
3. the cross-contract paths: collect to router to backstop; harvest to furnace; furnace buyback and
   backstop band in the same pool.
4. tests: gate:contracts 156 tests over 8 files at 100% lines/branches/functions, against the real
   v4 PoolManager and the real B20 precompile. Mainnet simulations (scripts/simulate-*.ts).
5. proof of concept for each new finding before writing it down (B1 has one in test/StageC.t.sol).

6. Slither 0.11.4 over contracts/src (2026-11-26): 59 results, all triaged as expected or false positives:
   reentrancy on functions already behind a lock or callable only by the PoolManager; ETH sent to fee
   recipients (by design); timestamps for the 7-day / 24-hour / 15-second windows (intended); ignored
   PoolManager return values that are not needed; missing zero checks on admin-proposed addresses.
7. invariant suite (test/Invariants.t.sol): random buys, sells, waits, gifts, pokes, collects and
   distributions, 512 runs x 256,000 calls, all holding: launch liquidity never shrinks; every band is placed
   under the price and every poke burns every coin it holds; the band climbs at most one spacing per 24 h;
   the router splits ETH 50/50 to the wei of rounding; burnt coins sit at the dead address.

8. more invariants (test/MoreInvariants.t.sol), same scale: the furnace keeps no coin but what the
   treasury refused, always holds the ETH it set aside, splits ETH 50/50, spends only what it set aside and
   burns to the dead address; BasketRouter never spends a standing approval for anyone but its owner, keeps
   no USDC or allowance, and charges a buyer exactly what the legs used.

Not done: formal verification and a second human. Those are the gaps an outside review would fill.

### V3-F1 / medium / a creator recipient can block `collect` for its own coin
From REVIEW-2026-10-29, still true on the live factory. `_push` sends ETH with all gas and Solidity copies the
return data, so a hostile recipient contract can burn the gas or return-bomb and revert `collect`. Only that
coin is affected; its protocol share (now the FeeRouter's) and referrer share stay in the pool. The recipient
loses its own 80% too, so the motive is griefing only. Fix needs a v4 factory (stipend + no return copy, as the
furnace already does). Recommend: do it with the next factory, not alone.

### B1, B2, B3 / Backstop
See REVIEW-2026-11-26.md. B1 (an empty poke held the band at the anchor) is confirmed by a PoC and fixed in
`src/Backstop.sol`; the live one is safe while a band stays placed, which it is since block 62,188,498.
B3 (band past the last usable tick on a worthless coin) fixed in source.

### R1 / low / BasketRouter trusts Relay's two approval proxies
Each leg calls one of two pinned Relay contracts with calldata nobody decodes; the only protection is the
exact approval per leg, the approval reset to zero, and the buyer's balance rising by `minOut`. Checked:
- it only ever pulls USDC from `msg.sender`, so a standing approval cannot be spent by anyone else;
- a leg cannot target USDC or any contract but the two proxies;
- calls Relay makes come from Relay's router, which holds no allowance from users of this contract;
- reentry is locked; leftover USDC goes back to the buyer in the same transaction.
Residual risk is Relay itself (a compromised proxy could take the leg's approved USDC, never more). Users
who prefer no standing approval use `buyWithPermit`.

### K1 / low / the keeper left $QUADRA in the router
The FeeRouter receives the protocol share of $QUADRA's pool in ETH AND in $QUADRA. The keeper distributed ETH
only, so the coin would have piled up in the router. Fixed: `scripts/keep-backstop.ts` now also calls
`distribute([QUADRA])` when the router holds any.

### F1, F2 / info / FeeRouter
A payee that refuses ETH stops `distribute` (both accept today; nothing is lost). The treasury can move the
protocol recipient after a public 7-day `announceMove` (the owner's chosen escape hatch).

### Q1 / info / QuadraFurnace
`buyAndBurn` is the treasury's alone, with a caller-chosen `minOut` against sandwiching; the pool has no
oracle, so a low `minOut` is the caller's risk. ETH to the treasury carries a 50,000 gas stipend: measured to
be enough for the treasury's EIP-7702 wallet.

## checked and fine

- LaunchFactoryV3: no path removes the launch liquidity; the supply is minted once with no admin on the B20;
  `msg.value` must equal the ETH first buy; a stock first buy is pulled from the caller only; quotes and their
  opening ticks bind NEW launches only; referrers only via the protocol recipient; a refused payout is kept in
  `owed`, never lost; `receive` takes ETH from the PoolManager only.
- LaunchHook: only the factory opens pools; nobody else adds liquidity during the 15 s window; the opening
  fee only falls; the factory's own first buy pays the chosen fee; no return-delta permissions (it cannot
  take a cut of a swap).
- QuadraFurnace: balance accounting keeps `toBuy` and `treasuryOwed` apart from fresh arrivals; burns go to
  `0x...dEaD` on an admin-less B20.
- FeeRouter / Backstop: see REVIEW-2026-11-26.md "checked and fine".
- Cross-contract: the furnace's buyback (buying the coin) moves the price away from the Backstop's band, never
  into it; both contracts' LP and swap use the same pool key read from the factory.

## recommendations, in order

1. Keep the Backstop funded so a band is always placed (B1 mitigation). The keeper does this as fees arrive.
2. Public wording: "internally reviewed, not independently audited". Never "audited".
3. When a new factory or Backstop is due anyway: ship V3-F1, B1, B3 fixes together, after fuzz/invariant tests.
4. Before larger TVL: run Slither + an invariant suite (backstop never loses ETH except to sellers; router
   always splits 50/50; factory never removes launch liquidity), then an outside review if revenue allows.
